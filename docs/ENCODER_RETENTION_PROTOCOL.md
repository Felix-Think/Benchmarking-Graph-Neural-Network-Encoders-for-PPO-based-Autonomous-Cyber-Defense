# Encoder x Observation-Retention Benchmark

Protocol approved in this conversation: three encoders, two training regimes,
five training seeds, sequential execution to 500000 simulator ticks using CPU rollout and a CUDA learner.

## Frozen Configuration

The single active configuration is `configs/experiments/encoder_retention_500k_cuda.json`.
This replaces the old 300k configurations and two-encoder launcher. Start new run
directories; preserve historical logs/checkpoints and do not relabel them as 500k.
Resume the same run with --resume --foreground; see RESUME.md.
Legacy checkpoints without a committed resume boundary are not silently migrated.

metrics; never auto-tune a cell or selectively restart a poor result.

## Full vs Mixed-q

Full means q=1: no additional masking, NOT full simulator state.
Mixed-q samples uniformly from {1,.75,.5,.25} once per episode. All five Blue
agents use the same q; each has its own deterministic, subnet-stratified host
selection. Retain round(q*N) hosts (round-half-up); the subset persists throughout
the episode. The q and mask RNGs are separate from PPO and simulator RNG.
Effective training q/mask seeds are40000+training_seed and30000+training_seed.
Episode seeds follow the existing training_seed+episode_index rule.

## Parallel Collection

Two workers collect four whole episodes per update under a single frozen copy
of the current policy. Results are joined in episode-index order before one PPO
update in the parent process. This is synchronous on-policy training, not two
independent policies or asynchronous gradient updates. Reward, GAE, masks,
encoder/head sizes and update grouping are unchanged. Evaluation stays serial.

For episode index i, the action seed is the first uint32 generated by NumPy
SeedSequence((70000, training_seed, i)). Each worker seeds Python, NumPy and Torch
with that value. A one-worker per_episode_v1 reference saves/restores these RNG
states around each rollout so optimizer minibatch shuffling is independent of
rollout draws. Simulator, q and visibility RNG rules are unchanged. This protocol
is not bitwise identical to the legacy global action RNG; all 30 new cells use
the same new protocol. Record action seeds in per-episode cyber metrics.

Parallel budget accounting assumes the current CAGE 4 fixed episode duration
of episode_steps-1 actual ticks and fails explicitly if an episode violates it.
The final update requests only the required number of complete episodes.
Every worker has its own temporary PyG cache to avoid concurrent writes to
generated message-passing modules. Worker processes are closed before final
evaluation and on exit. CPU regression tests cover the collection path. Real CUDA integration tests must
pass on the target NVIDIA GPU before the long run; M4 cannot validate CUDA.

Read `rl/rollout/parallel.py` for worker setup and RNGs, `rl/ppo/training.py` for
batching and budget, and `scripts/training/train.py` for pool lifetime/logging.
Tests cover sequential/parallel equality for all three encoders and both regimes,
partial final updates, milestone checkpoints and train/eval integration.

This is output-level masking AFTER the canonical memory update. It zeros host
dynamic features, including sensor evidence and some decoy/analysis state; it
keeps static identity, topology/matrices, global features, rewards and official
mask. It is not sensor-only dropout, physical host deletion or subnet isolation.
No explicit missingness feature is added. Zero features can be ambiguous; this
is a limitation of the agreed unchanged schema. No claim of complete information
removal through all channels is justified.

Episode cyber records store q and the retained host node indices. Training logs
include q counts, allowing verification of the sampled mixture. Full and mixed-q
share all other settings. No mixed-q evaluation averaging: report each q alone.

## Checkpoints and Evaluation

Save a complete training checkpoint after the first PPO update crossing100k,
200k,300k,400k,500k. With499 ticks/episode and4 episodes/update, expected actual
ticks are101796,201596,301396,401196,500497 (1003 episodes,251 updates at final).
The 300k milestone is now an intermediate full update, unlike the final shortened
update in the old experiment. Always report measured values. Do not shorten a rollout
or change the update grouping just to hit an exact nominal checkpoint.

At each milestone, stochastic validation runs10 episodes separately at each q,
using environment/action seeds20000 onward and mask seed50000. Periodic q=1
validation every25 updates selects a secondary best checkpoint; do not mix that
selection with the final-budget primary checkpoint.

After500k, test the final checkpoint at each q with30 episodes, environment/action
seeds10000 onward and mask seed50000. Stochastic is primary, greedy diagnostic.
Both use the same episode seeds; q=1 reuses the existing final evaluation rather
than running it twice. Random streams are restored around in-training evaluation.
Paired seeds do not imply identical trajectories once actions differ.

latest_checkpoint.pt is atomically replaced after every completed update and its
validation callbacks. It includes policy, optimizer, counters, RNGs, metrics and
periodic/best selection state. An initial checkpoint covers the first rollout.
Resume restores this boundary; interrupted uncommitted work is replayed.
Milestone checkpoints saved before validation are not resumable boundaries.
Continuous runs do not restart at milestones. See RESUME.md for limits.

## Metrics and Interpretation

Raw team return; OT availability; GreenLocalWork/GreenAccessService success;
privileged compromise burden; number of currently compromised hosts at episode
end and unique compromised hosts during the episode; successful Impact per tick,
attempts and successes; OT completed TTR and recovery/unrecovered counts/rate.
`compromised_host_count` is the episode-END count, not a time average.
TTR is conditional on completed recoveries; never interpret alone or turn missing
values into0. Training additionally reports PPO stability and compute throughput.

Use equal episode weight within a training seed, then sample standard deviation
across the five training seeds. Preserve raw episodes and censored recovery
events. Training episodes use changing policies; pooled training summaries are
descriptive, not final-policy evaluation scores. No untested convergence claim.
Compute metrics include rollout/update/evaluation wall time, CPU time, sampled
process-tree peak RAM and learner CUDA peak allocated/reserved memory. Compare
on the same hardware/software allocation; see COMPUTE_METRICS.md and COLAB_CUDA.md.
Earlier evidence qualification does not prove all new encoders exploit evidence
or that every retention level is learnable.

## Running and Monitoring

Preview with:

```zsh
uvr python -m scripts.experiments.run_encoder_matrix \
  --config configs/experiments/encoder_retention_500k_cuda.json \
  --run-root runs/encoder_retention_500k_5seeds_cuda
```

Add `--launch` to start a detached sequential queue. This saves the configuration,
source archive, source fingerprint and current git diff before launching. Existing
run directories are refused unless --resume is specified. The queue finishes six
cells per seed, in order42 through46.

Each cell has console.log, config.json, training_history.jsonl, TensorBoard logs,
checkpoint.pt, and milestones/step_N/checkpoint.pt.
Milestones also store training_summary.json and validation_retention.json.
Final metrics live in evaluation_retention.json and the existing mode-specific JSON.
The root status.json records current/completed jobs and any failure.

The queue stops if source changes before the next job. To finish the current job
and prevent further jobs, create STOP_AFTER_CURRENT at the run root. An immediate
stop requires signalling the queue process; it forwards the interruption to the
current child. No automatically restarting failed jobs or overwriting logs.

Monitor only at meaningful changes: milestone, completed cell/seed, failure, or
non-finite output. Sparse checks every hour; no detailed per-update narration.
Never adjust parameters based on final-test scores. A protocol change after
validation requires a new named experiment and retaining the old results.
